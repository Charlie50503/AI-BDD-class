# 原則

- 使用者明確確認類別圖之前，不寫入任何程式碼檔案。
- 類別圖只畫本次開發會碰到的類別：新增的、要修改的，以及它們直接相依的既有類別。
- 在類別圖中用 `<<new>>`、`<<modified>>` 標出每個類別的狀態，沒有標記的就是不變動的既有類別。
- 關係用 Mermaid 語法表示：組成 `*--`、聚合 `o--`、繼承 `<|--`、實作 `<|..`、相依 `..>`。

# SOP

## Phase 1 — 需求與現況清單

1. READ 使用者的開發需求，以及專案中與需求相關的既有類別與介面。
2. WRITE 在回覆中列出本次開發涉及的類別，逐一標明是新增、修改，還是不變動的既有類別。

出口條件：回覆中有一份類別清單，每個類別都標了新增、修改或既有其中一種狀態。

## Phase 2 — 已確認的類別圖

1. THINK 依類別清單決定每個類別的職責、主要屬性與方法，以及類別之間的關係。
2. WRITE 在回覆中輸出一段 ```mermaid classDiagram``` 程式碼區塊，並在區塊後詢問使用者：「這個類別設計可以嗎？確認後我就開始實作。」然後結束這一輪回覆，等使用者回應。
3. READ 使用者的回應。如果是修改意見，就依意見回到步驟 1 重畫類別圖；如果是明確同意，就進入下一個 Phase。

出口條件：使用者最新一則回覆明確同意最後一版類別圖。

## Phase 3 — 施工順序清單

1. THINK 依已確認類別圖的關係找出相依順序：被依賴、被組成或被繼承的類別排在前面，依賴它們的類別排在後面。
2. WRITE 在回覆中列出編號的施工順序，每一項寫出類別名稱，以及它依賴的前序類別。

出口條件：回覆中有一份施工順序清單，列出類別圖中所有標為 `<<new>>` 或 `<<modified>>` 的類別，而且每個類別都排在它依賴的類別之後。

## Phase 4 — 依序實作的程式碼

1. WRITE 依施工順序逐一建立或修改類別，每個類別的屬性、方法與關係都要和已確認的類別圖一致。
2. READ 完成的程式碼，逐一對照類別圖中的類別、屬性、方法與關係。
3. WRITE 修正對照時發現的差異。如果實作時需要偏離類別圖，就在回覆中列出偏離項目和原因。

出口條件：類別圖中每個標為 `<<new>>` 或 `<<modified>>` 的類別，都已在程式碼中出現，而且和類別圖一致；有偏離的地方，也都已在回覆中列出。
